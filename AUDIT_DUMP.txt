# Block 0: System Overview — Data Flow, Boundaries, and Integration Points

This document defines the top-level system: what enters, what leaves, which subsystems exchange what, and where the boundaries of the platform lie. It is the reference map for all other architecture documents.

---

### 1. System Boundaries

The DAXSI platform is defined by four boundaries. Anything outside them is not part of the system.

| Boundary | Defined by | Excludes |
|---|---|---|
| Physical | Cybertruck envelope + CyberHab pod + deployed manipulator + portable kit radius | External infrastructure, fixed base stations |
| Compute | Node 01 + Node 02 + Node 03 | Cloud clusters, xAI data centers |
| Data | Sensor matrix + empirical vault + knowledge graph | Open web, social media, scraped corpora |
| Authority | Human operator in the loop | Autonomous decision without human arbitration |

The platform is self-sufficient within these boundaries. It does not require continuous connectivity to function.

---

### 4. Operational States

The platform operates in four states. Transitions are controlled by the operator or by autonomous logic with human override.

| State | Description | Compute draw | Sensors | Manipulator | Starlink |
|---|---|---|---|---|---|
| **Idle** | Parked, low-power monitoring | 0.2 kW | Minimal | Stowed | Off |
| **Static monitoring** | Stationary observation, weeks | 1.5 kW | Full | Stowed | Periodic |
| **Mobile survey** | Driving, data collection | 2.3 kW | Full | Stowed | Off |
| **Deployed** | Stationary, manipulator active, kit deployed | 2.3 kW | Full | Active | On |

State transitions are logged with timestamps and operator ID.

---

### 5. Failure Modes and Degradation

The platform is designed to degrade, not to fail abruptly.

| Failure | Effect | Mitigation | Status |
|---|---|---|---|
| Node 02 loss | Inference degraded | Fall back to Node 01 backbone (smaller model) | `[COTS]` |
| Node 03 loss | RAG unavailable | Local cache on Node 02 continues | `[COTS]` |
| Starlink loss | No orbital validation | Full local autonomy continues | `[COTS]` |
| Sensor loss | Partial perception | Redundant coverage from overlapping sensors | `[COTS]` |
| Coolant leak | Thermal throttling | Automatic derating, operator alert | `[COTS]` |
| Powershare loss | Battery-only operation | Static monitoring continues at 1.5 kW | `[COTS]` |
| HSLDS failure | Reduced vibration isolation | Wire-rope isolators remain functional | `[PROTO]` |

No single failure removes the platform's ability to collect data and preserve it locally.

---

### 6. Integration Points

The platform is designed to integrate with external systems without depending on them.

| External system | Integration | Dependency |

| Operator | Voice, console, portable kit | Required |

The platform is functional without xAI and without Starlink. It is not functional without an operator.

# Block 1: Compute Cluster — Node Topology, Hardware, and Expansion Path

This document defines the compute architecture of the DAXSI platform. It replaces the previous fixed-VRAM specification with a block-scalable topology: a validated baseline that can be expanded through defined nodes without redesigning the system.

---

### 1. Design Principle

The cluster is organized by function, not by capacity. Each node has a distinct role, a distinct failure mode, and a distinct expansion path. Capacity is a consequence of the topology, not a target.

| Principle | Implementation |
|---|---|
| Functional separation | Command, inference, and storage are separate nodes |
| Fail-degraded | Loss of any node degrades capability, does not stop operation |
| Block-scalable | Each node can be expanded independently |
| Galvanic isolation | Optical links between nodes |
| Thermal isolation | Each node has its own coolant loop segment |

---

### 2. Baseline Topology

| Node | Role | Hardware | VRAM | Power (peak) | Status |
|---|---|---|---|---|---|
| 01 | Command Core | 2× Jetson AGX Orin 64GB | 128 GB | 0.12 kW | `[COTS]` |
| 02 | Inference Primary | 4× RTX 6000 Ada 48GB | 192 GB | 1.2 kW | `[COTS]` |
| 03 | RAG / Storage | 8× Jetson Orin NX 16GB | 128 GB | 0.16 kW | `[COTS]` |
| **Baseline total** | | | **448 GB** | **1.48 kW** | |

The baseline is fully COTS. Every component is available today.

---

### 3. Node Roles

#### Node 02 — Inference Primary

Node 02 is the primary reasoning engine. It runs the local backbone model and the multi-spectral vision pipeline.

| Parameter | Value |

| Index target | Pre-loaded academic baseline + field logs |

Node 03 is the memory of the platform. It does not generate; it retrieves and indexes.

---

### 4. Expansion Path

The baseline is not the ceiling. Each node has a defined expansion path.

| Stage | Node 02 | Node 03 | Total VRAM | Status |
|---|---|---|---|---|
| Baseline | 4× RTX 6000 Ada (192 GB) | 8× Orin NX (128 GB) | 448 GB | `[COTS]` |
| Stage 1 | 8× RTX 6000 Ada (384 GB) | 8× Orin NX (128 GB) | 640 GB | `[COTS]` |
| Stage 2 | 8× RTX 6000 Ada (384 GB) | 4× L40S (192 GB) | 704 GB | `[COTS]` |
| Stage 3 | External dock | External dock | ~1 TB | `[CONCEPT]` |

Stage 1 requires a second PCIe chassis in the Vault. Stage 2 replaces the Jetson array with L40S cards. Stage 3 is a trailer or static dock and is not part of the vehicle envelope.

The hard ceiling is not VRAM availability. It is the Cybertruck Powershare power and thermal envelope. At 9.6 kW continuous, the platform cannot sustain more than approximately 2.5 kW of compute without exceeding headroom for cooling and ECLSS.

# Block 2: Sensor Matrix — Full-Spectrum Perception by Physical Field

This document defines the sensor architecture of the DAXSI platform. Sensors are organized by physical field, not by device list. Each field maps to the best available COTS instrument for a moving platform, with explicit selection rationale.

---

### 1. Design Principle

The sensor matrix is a perception system, not a collection of instruments. Each sensor is selected against four criteria.

| Criterion | Requirement |
|---|---|
| Spectral coverage | Fills a gap not covered by another sensor |
| Motion tolerance | Operates under vehicle vibration and motion |
| Environmental rating | IP67 or better, −40 °C to +85 °C |
| Interface | GigE, GMSL2, USB 3.0, or UART with ROS 2 driver |

Pushbroom hyperspectral instruments are excluded from the mobile platform. They require stable motion and produce distortion under vibration. Snapshot instruments are preferred wherever the spectral range permits.

---

### 2. Physical Field Map

| Field | Sub-range | Sensor | Weight | Interface | Status |
|---|---|---|---|---|---|
| EM — optical | UV–VIS 350–1000 nm | Cubert ULTRIS X20 | 350 g | GigE | `[COTS]` |
| EM — optical | VNIR 400–1000 nm | Specim AFX10 | 2.4 kg | GigE | `[COTS]` |
| EM — optical | SWIR 900–1700 nm | ATH1700-17 | 1.1 kg | GigE | `[COTS]` |
| EM — optical | SWIR ext. 960–2500 nm | Specim SX25 | 4.0 kg | GigE | `[COTS]` |
| EM — thermal | LWIR 7.7–12.3 µm | FLIR Boson 640 | 7.5 g | GMSL2 / USB | `[COTS]` |
| EM — ranging | 905 / 1550 nm | Ouster OS1-128 | 950 g | Ethernet UDP | `[COTS]` |
| EM — ionizing | gamma / beta | SBM-20 Geiger | 40 g | UART | `[COTS]` |
| EM — magnetic | 3-axis | Fluxgate magnetometer | 80 g | I2C / UART | `[COTS]` |
| Chemical | VOC, CO2, CH4, NOx | Bosch BME680 + NDIR + electrochemical cells | 30 g | I2C / UART | `[COTS]` |
| Acoustic | audible + infrasound | ReSpeaker Mic Array v2.0 | 120 g | USB Audio | `[COTS]` |
| Kinetic | 9-DOF | Bosch BNO055 | 5 g | I2C | `[COTS]` |

---

### 3. Selection Rationale

#### Optical — Hyperspectral

| Instrument | Type | Rationale |
|---|---|---|
| Cubert ULTRIS X20 | Snapshot | 164 channels, 350–1000 nm, no moving parts, tolerant to vibration |
| Specim AFX10 | Pushbroom | Fixed-wing baseline reference, not for mobile use |
| ATH1700-17 | Snapshot | 25 fps, 100 channels, 900–1700 nm, direct mineral and moisture discrimination |
| Specim SX25 | Pushbroom | 960–2500 nm, 392 channels, full chemical signature, static deployment only |

The mobile platform carries ULTRIS X20 and ATH1700-17 as primary hyperspectral instruments. AFX10 and SX25 are ground-truth references, deployed from the portable kit or static station.

#### Optical — Thermal

FLIR Boson 640 is selected over larger LWIR instruments because of its 7.5 g mass, 640×512 resolution, and GMSL2 interface. A larger LWIR hyperspectral instrument (Specim AisaOWL, 13.1 kg) is excluded from the mobile platform and reserved for static deployment.

#### Ranging

Ouster OS1-128 provides 200 m range, 5.2M points/s, IP68/69K rating, and −40 °C operation. It is the only LiDAR in the selection that meets all four criteria without modification.

#### Chemical

The chemical suite is layered: BME680 for general air quality, NDIR for CO2 and CH4, electrochemical cells for specific gases. No single sensor covers the full chemical field.

#### Acoustic

ReSpeaker Mic Array v2.0 provides 4-microphone spatial audio with USB Audio Class interface. Infrasound coverage is limited to 20 Hz; sub-20 Hz detection requires a dedicated geophone, which is not in the baseline.

---

### 4. Spatial Placement

| Location | Sensors | Rationale |
|---|---|---|
| Roof ridge platform | LiDAR, LWIR, panoramic VIS, weather station | Above aerodynamic and thermal boundary layer |
| A-pillars and side sails | UV/VIS matrices, side LiDAR | Zero blind spots for volumetric mapping |
| Vault tailgate edge | Ground-facing stereo, Geiger tube | Terrain tracking, radiation isolated from cabin electronics |
| Underbody (protected) | IMU, magnetometer | Chassis reference, magnetic field measurement |
| Portable kit | Handheld spectroradiometer, gas analyzer | Locations inaccessible to the vehicle |

All sensors are mounted on vibration-isolated platforms. See `07_isolation_enclosure.md`.

---

### 5. Data Ingestion Pipeline

| Stage | Technology | Function |
|---|---|---|
| Capture | GigE Vision, GMSL2, USB 3.0 | Raw sensor streams |
| Transport | iceoryx shared memory | Zero-copy to inference nodes |
| Peripheral telemetry | ESP-NOW mesh | Low-frequency sensor data, bypasses main network |
| Time sync | IEEE 1588 PTP | Microsecond alignment across all nodes |
| Storage | MCAP, Parquet | Time-series and geospatial indexing |
| Ground truth | RTK-GPS + IMU | Every record tagged with position and orientation |

Time synchronization is the foundation of the pipeline. A gas surge, an optical frame, and a LiDAR return must be aligned to the same timestamp before they can be correlated.

---

### 6. Calibration and Ground Truth

Every sensor requires calibration against a known reference before field deployment.

| Sensor | Calibration method | Frequency |
|---|---|---|
| Hyperspectral | Spectralon reference panel | Before each mission |
| Thermal | Blackbody reference | Monthly |
| LiDAR | Surveyed targets | Before each mission |
| Gas | Certified gas mixtures | Monthly |
| Radiation | Known source | Annually |
| IMU | Static and dynamic bench | Before each mission |

Calibration records are stored in the empirical vault with timestamps. An uncalibrated sensor is excluded from the dataset.

---

### 7. Open Questions

1. SWIR snapshot sensor (ATH1700-17) field reliability under vibration is not validated.
2. Infrasound coverage below 20 Hz requires a geophone not in the baseline.
3. Hyperspectral data volume (up to 800 MB/s) requires real-time compression strategy not yet defined.
4. ESP-NOW mesh range under vehicle body obstruction requires field measurement.

See `01_FEASIBILITY/open_questions.md`.

### 7. Thermal Integration

The pod has three thermal paths.

| Path | Source | Destination | Status |
|---|---|---|---|
| Liquid loop A | Node 02 RTX cluster | Roof radiator behind solar array | `[COTS]` |
| Liquid loop B | Node 01 command core | Chassis-contact cooling blocks | `[COTS]` |
| PCM buffer | Node 02 waste heat | Cabin heating during cold cycles | `[COTS]` |

Loop A rejects heat to the roof radiator. Loop B rejects heat to the chassis structural mass during cold-weather operation. The PCM buffer stores excess heat during operation and releases it during cold static periods.

# Block 4: AI Layer — Local Backbone, Orbital Validation, and Human-in-the-Loop

This document defines the AI architecture of the DAXSI platform. The layer is split into three tiers with distinct roles: local inference, orbital validation, and human arbitration. No tier is optional except the orbital one.

---

### 1. Design Principle

The AI layer is model-agnostic at the edge and xAI-aligned at the orbit. This is a deliberate split.

| Tier | Location | Role | Dependency |
|---|---|---|---|
| Local backbone | Node 02, Node 01 | Inference, vision, routing | None |
| Orbital validation | xAI Grok via Starlink | Cross-check, enrichment, weight updates | Starlink link |
| Human-in-the-Loop | Operator console | Arbitration, annotation, training trigger | Operator |

The platform is functional without the orbital tier. It is not functional without the human tier.

---

### 2. Local Backbone

| Parameter | Value | Status |
|---|---|---|
| Model class | Open-weights 70B | `[COTS]` |
| Quantization | 4-bit AWQ | `[COTS]` |
| Execution platform | Node 02, 4× RTX 6000 Ada | `[COTS]` |
| Inference engine | vLLM, TensorRT-LLM | `[COTS]` |
| Latency target | < 2 s for 1k-token generation | `[COTS]` |
| Model identity | Model-agnostic; any open-weights checkpoint | `[COTS]` |

The local backbone is not tied to a specific model family. The checkpoint is a configuration parameter, not an architectural commitment. This allows substitution as open-weights models improve.

#### Command-tier model

| Parameter | Value | Status |
|---|---|---|
| Role | Voice, routing, fast context | `[COTS]` |
| Hardware | Node 01, 2× Jetson AGX Orin | `[COTS]` |
| Model class | 9B, FP16/INT8 | `[COTS]` |
| Voice pipeline | Whisper Large v3 | `[COTS]` |
| Latency target | < 300 ms round-trip | `[COTS]` |

---

### 3. Orbital Validation Layer

| Parameter | Value | Status |
|---|---|---|
| Provider | xAI Grok | `[COTS]` |
| Transport | Starlink Mobility | `[COTS]` |
| Payload | Compressed knowledge graphs, not raw data | `[COTS]` |
| Direction | Bidirectional | `[COTS]` |
| Frequency | Periodic, operator-triggered or scheduled | `[COTS]` |

The orbital layer does not receive raw sensor data. It receives compressed, structured knowledge graphs: mathematical representations of what was detected and how it was interpreted. This preserves bandwidth and keeps raw empirical data local.

The orbital layer returns validated graphs and, optionally, adapter weights. It does not return base model weights.

---

### 4. Human-in-the-Loop Pipeline

The operator is not a user. The operator is the scientific mentor.

| Stage | Action | Trigger |
|---|---|---|
| Detection | Vision core flags anomaly | YOLOv11 multi-spectral |
| Alert | Operator notified on console | Anomaly score threshold |
| Validation | Operator tags, corrects, annotates | Voice or console |
| Storage | Validated log written to empirical vault | Confirmation |
| Training | LoRA/QLoRA on validated logs | Static state or overnight |
| Deployment | Adapter weights loaded into backbone | After validation |

The operator's corrections are the ground truth. The model does not self-validate.

---

### 5. Cascading RAG Architecture

The knowledge base is fully local. It has three tiers.

| Tier | Location | Content | Latency |
|---|---|---|---|
| 1 | Node 02 VRAM partition | Active session embeddings (current 50 km radius) | Microseconds |
| 2 | Node 03 Jetson array | Pre-loaded academic baseline (physics, chemistry, materials, geology, biomimetics) | Milliseconds |
| 3 | Empirical vault NVMe | Raw sensor logs, append-only | Seconds |

Tier 1 is ephemeral. Tier 2 is the sovereign knowledge graph. Tier 3 is the immutable record.

The vector database runs on Node 03 using Milvus or Qdrant. Index size for the full academic baseline on 128 GB VRAM is an open question. See `01_FEASIBILITY/open_questions.md`.

---

### 6. Fine-Tuning Pipeline

| Parameter | Value | Status |
|---|---|---|
| Method | LoRA / QLoRA | `[COTS]` |
| Trigger | Static monitoring state or overnight charging | `[COTS]` |
| Data source | Validated operator logs only | `[COTS]` |
| Base weights | Frozen | `[COTS]` |
| Adapter storage | Empirical vault, versioned | `[COTS]` |
| Rollback | Previous adapter preserved | `[COTS]` |

Fine-tuning never modifies base model weights. Adapters are versioned and can be rolled back. An adapter that degrades performance on a held-out validation set is rejected.

---

### 7. Failure and Degradation

| Failure | Effect | Mitigation |
|---|---|---|
| Node 02 loss | Heavy inference unavailable | Node 01 command model continues |
| Starlink loss | No orbital validation | Local autonomy continues |
| Node 03 loss | RAG unavailable | Tier 1 cache continues |
| Operator unavailable | No arbitration | Platform enters Idle state |
| Adapter corruption | Degraded model | Rollback to previous adapter |

The AI layer degrades gracefully. It does not fail closed.

# Block 7: Isolation Enclosure Architecture — EMI, Vibration, Thermal Feedthroughs

This document defines the physical enclosure of every compute block in the DAXSI platform. The enclosure is treated as a subsystem, not as sheet metal. Each layer addresses a distinct physical threat: kinetic load, vibration, electromagnetic interference, and thermal exchange.

---

### 1. Threat Model

The Cybertruck platform exposes onboard compute to four overlapping threats that are absent in a data center.

| Threat | Source | Frequency / Range | Consequence |
|---|---|---|---|
| Kinetic impact | Debris, terrain strike, cargo shift | Impulse | Structural deformation, connector shear |
| Vibration | Drivetrain, off-road surface, manipulator motion | 5–500 Hz | Solder fatigue, connector wear, sensor drift |
| EMI — electric | Traction inverter, motor phases, Powershare | 10 kHz–1 GHz | Data corruption, clock jitter |
| EMI — magnetic | Motor fields, external sources | 50 Hz–100 kHz | Inductive coupling into signal lines |
| Thermal | GPU clusters, solar gain, external ambient | Continuous | Derating, throttling |
| Moisture / dust | Wading, dust storms, condensation | Continuous | Corrosion, short circuit |

Each layer of the enclosure addresses one or more of these threats. No single layer addresses all.

---

│
▼

#### L1 — Aluminum Structural Shell

| Parameter | Value | Status |
|---|---|---|

Aluminum provides electric-field attenuation but does not provide magnetic shielding. Magnetic attenuation is delegated to L3.

#### L2 — Aluminum Foam Damping Layer

| Parameter | Value | Status |
|---|---|---|
| Material | Closed-cell aluminum foam | `[COTS]` |

The foam is bonded to the inner wall of L1. It dissipates vibration energy through micro-plastic deformation of the cell walls. This layer is passive and requires no power.

#### L3 — EMI Inner Liner

| Parameter | Value | Status |
|---|---|---|
| Material | Faraday CYBER NC-Berry Rip Stop | `[COTS]` |
| Construction | Nickel-copper plated polyester ripstop | `[COTS]` |
| Attenuation | 75 dB, 100 MHz–18 GHz | `[COTS]` |
| Thickness | 7 mil | `[COTS]` |

| Function | Magnetic and electric field shielding, seam closure | `[COTS]` |

The two layers are offset so that seams do not align. Overlap regions are bonded with conductive adhesive. Cable and optical penetrations are wrapped and bonded to the liner to preserve shield continuity.

#### L4 — Passive Vibration Isolation

| Parameter | Value | Status |
|---|---|---|
| Type | Wire-rope isolator | `[COTS]` |
| Mounting | Four-point per chassis | `[COTS]` |

| Function | Broadband passive isolation, no power required | `[COTS]` |

Wire-rope isolators are selected over elastomeric mounts because they tolerate temperature extremes, do not degrade under UV, and do not outgas in a sealed enclosure.

#### L5 — Adaptive Vibration Isolation

| Parameter | Value | Status |
|---|---|---|
| Type | HSLDS magnetic-pneumatic module | `[PROTO]` |
| Mounting | One per chassis, in series with L4 | `[PROTO]` |
| Function | Tunable negative stiffness, low-frequency isolation | `[PROTO]` |
| Control | ROS 2 node, accelerometer feedback | `[PROTO]` |

HSLDS modules are at prototype maturity. They are not required for Phase 0 or Phase 1. Phase 2 introduces them after bench validation. See `01_FEASIBILITY/open_questions.md`.

#### L6 — Optical Ports

| Parameter | Value | Status |
|---|---|---|
| Type | ODU Expanded Beam | `[COTS]` |
| Standard | MIL-DTL-38999 / VITA 95/96 | `[COTS]` |
| Insertion loss | < 0.15 dB multimode | `[COTS]` |
| Mating cycles | 50,000 without cleaning | `[COTS]` |

Expanded-beam construction uses a lens instead of physical fiber-end contact. This removes the primary failure mode of optical connectors in field conditions: contamination of the fiber end face. All inter-block data links use this port type. No copper data cables cross the enclosure boundary.

#### L7 — Coolant Feedthroughs

| Parameter | Value | Status |
|---|---|---|
| Type | Hermetic bulkhead fitting | `[COTS]` |

Coolant lines are non-conductive and pass through the shield at a single bonded penetration. The feedthrough body is electrically bonded to L1 and L3 to preserve shield continuity.

### 5. Static Monitoring Budget

Static monitoring is the longest-duration state. It determines battery endurance.

| Load | Draw (kW) |
|---|---|
| Node 01 | 0.08 |

| Node 03 | 0.12 |

| Sensors | 0.10 |
| **Total** | **1.05** |

With solar input of 0.6 kW average (50% of peak, accounting for angle and weather), net draw is 0.45 kW. Cybertruck traction battery capacity is approximately 123 kWh. At 0.45 kW net draw, endurance is approximately 270 hours, or 11 days, without recharging.

| STC thermal harvester | 812% reduction in cooling load | `[PROTO]` |
| PCM buffer | Shifts heating load from battery to stored heat | `[COTS]` |

STC does not generate net power. It reduces the cooling load by converting low-grade heat to 48V rail current. The 812% estimate is from data-center PoC, not vehicle validation.

---

### 7. Open Questions

1. STC contribution in vehicle thermal environment is not validated.
2. Static monitoring endurance under overcast conditions requires field measurement.
3. Manipulator peak draw during dynamic motion exceeds the 0.30 kW estimate in some commercial arms. Requires measurement.
4. Portable kit charging while deployed reduces Deployed state headroom.

See `01_FEASIBILITY/open_questions.md`.

# Thermal Budget  Heat Generation, Rejection, and Harvesting

This document defines the thermal budget of the DAXSI platform. It covers heat generation by node, rejection paths, PCM buffering, and STC harvesting. The binding constraint is roof radiator area, not coolant capacity.

---

### 1. Heat Generation by Node

| Node | Electrical draw (kW) | Heat load (kW) | Notes |
|---|---|---|---|
| Node 01 | 0.12 | 0.12 | Near 100% to heat |
| Node 02 | 1.20 | 1.20 | Near 100% to heat |
| Node 03 | 0.16 | 0.16 | Near 100% to heat |
| Cooling pumps | 0.10 | 0.05 | Partial to heat |
| PDU losses | 0.05 | 0.05 | Conversion losses |
| **Total compute heat** | | **1.58** | Peak |

All electrical power drawn by compute becomes heat. The only exception is optical power emitted by sensors, which is negligible.

---

### 2. Rejection Paths

| Path | Capacity (kW) | Medium | Status |
|---|---|---|---|
| Loop A  roof radiator | 1.50 | Liquid-to-air | `[COTS]` |
| Loop B  chassis contact | 0.40 | Conduction | `[COTS]` |
| PCM buffer | 0.30 (transient) | Phase change | `[COTS]` |
| STC harvester | 0.15 (recovery) | Thermal-to-electric | `[PROTO]` |
| **Total rejection** | **2.35** | | |

Total rejection capacity exceeds peak heat load by 0.77 kW. This margin covers ambient temperature derating.

---

### 3. Roof Radiator Sizing

| Parameter | Value | Status |
|---|---|---|
| Area | 1.8 m | `[COTS]` |
| Coolant inlet temp | 55 C | `[COTS]` |
| Ambient temp (design) | 40 C | `[COTS]` |
| Delta-T | 15 C | `[COTS]` |
| Airflow (vehicle moving) | 15 m/s | `[COTS]` |
| Rejection capacity | 1.50 kW | `[COTS]` |

At 40 C ambient and 15 m/s airflow, a 1.8 m radiator rejects approximately 1.50 kW. This is sufficient for Node 02 at average load, but not at peak. Peak load is handled by PCM buffering.

In static monitoring, airflow is zero. Radiator capacity drops to approximately 0.40 kW by natural convection. This is why PCM buffering is required for static states.

---

### 4. PCM Buffer

| Parameter | Value | Status |
|---|---|---|
| Material | Paraffin-based phase-change material | `[COTS]` |
| Mass | 25 kg | `[COTS]` |
| Melting point | 58 C | `[COTS]` |
| Latent heat | 200 kJ/kg | `[COTS]` |
| Total storage | 5.0 MJ | `[COTS]` |
| Charge time (peak load) | 45 min | `[COTS]` |
| Discharge time (cabin heating) | 8 hours | `[COTS]` |

The PCM buffer absorbs heat during peak inference and releases it during cold static periods. It is not a net energy source; it is a time-shift buffer.

At 0.30 kW transient absorption, 5.0 MJ provides approximately 4.6 hours of buffering. This covers the gap between peak inference and radiator capacity.

---

### 5. STC Thermal Harvester

| Parameter | Value | Status |
|---|---|---|
| Technology | Semiconductor-sensitized thermal cell | `[PROTO]` |
| Operating temperature | 3080 C | `[PROTO]` |
| Conversion efficiency | 13% | `[PROTO]` |
| Output | 48V DC, 0.050.15 kW | `[PROTO]` |
| Integration point | Loop A return line | `[PROTO]` |

STC is not a primary power source. It recovers low-grade heat that would otherwise be rejected to ambient. At 13% efficiency and 1.5 kW heat flow, output is 0.0150.045 kW. The 0.15 kW upper estimate assumes a larger array than the baseline.

STC is a Phase 2 item. It is not required for Phase 0 or Phase 1.

---

### 6. Cold-Weather Operation

| Scenario | Heat source | Status |
|---|---|---|
| Cabin heating, engine off | PCM buffer | `[COTS]` |
| Cabin heating, compute active | Node 02 waste heat via liquid-to-air | `[COTS]` |
| Battery warming | Chassis contact loop B | `[COTS]` |
| Extreme cold (30 C) | PCM + heat pump | `[COTS]` |

At 30 C ambient, radiator capacity is irrelevant. All heat is retained. The PCM buffer and Node 02 waste heat provide cabin heating without drawing from the traction battery.

This is the primary value of the thermal architecture: in cold conditions, waste heat is a resource, not a problem.

---

### 7. Thermal Derating

| Condition | Derating | Mitigation |
|---|---|---|
| Ambient > 45 C | Node 02 throttles to 60% | PCM buffer, reduced inference |
| Radiator blocked | Node 02 throttles to 40% | Operator alert, cleaning |
| Coolant leak | Node 02 shuts down | Failsafe to Node 01 |
| Static, no airflow | Node 02 limited to 0.40 kW | PCM buffer |

Derating is graceful. The platform does not shut down; it reduces capability.

---

### 8. Open Questions

1. Radiator capacity at 40 C ambient and 15 m/s airflow requires wind-tunnel validation.
2. PCM discharge time under 30 C ambient requires thermal simulation.
3. STC efficiency at vehicle-scale heat flow is unvalidated.
4. Chassis contact cooling capacity depends on vehicle thermal mass, not measured.

See `01_FEASIBILITY/open_questions.md`.

===== FILE: PHILOSOPHY.md =====

# Philosophy - From Text to Physical Reality

---

### I. The Limit of Text

For the past decade, frontier AI has been trained on the internet. This corpus is a closed loop: human writing, synthetic noise, and structural bias. A model trained on it learns what humans have written about the world. It does not learn the world.

The result is a system that can describe a mineral but has never measured one. It can explain a physical law but has never tested it. It can generate a hypothesis but cannot collect the data that would confirm or reject it.

This is not a limitation of model size. It is a limitation of input. No amount of text produces empirical ground truth.

---

### II. The Kinetic Instrument

DAXSI is a response to that limit. It is not a vehicle with a server. It is a sensor-and-compute platform that moves through the physical world and measures it directly.

The platform has three properties that text-based AI lacks:

| Property | Consequence |
|---|---|
| Physical presence | Direct measurement, not description |
| Motion | Access to terrain and phenomena beyond fixed installations |
| Local compute | Autonomy without network dependency |

The platform does not replace text-based AI. It gives it a body.

---

### III. First-Principles Data

The data collected by DAXSI is first-principles in a specific sense: it is measured, not written. It comes from sensors calibrated against known references, timestamped to microsecond precision, and tagged with position and orientation.

This data is not free of error. It is free of the structural bias that comes from training on human text. A spectral measurement of a mineral does not care what humans have written about that mineral.

The platform does not claim to produce absolute truth. It claims to produce data that can be checked against physical reality, independently of any text corpus.

---

### IV. The Human as Mentor

The operator is not a user. The operator is the scientific mentor.

The platform observes, detects anomalies, and generates hypotheses. The operator validates, corrects, and annotates. The model does not self-validate. It learns from the operator's judgment, not from its own output.

This relationship is deliberate. An autonomous system that trains on its own output drifts. An autonomous system that trains on validated human judgment improves.

---

### V. Data Sovereignty

The data collected by the platform belongs to the operator. It is stored locally, encrypted at rest, and transferred only with explicit consent.

This is not a political statement. It is an engineering requirement. A scientific instrument that cannot guarantee the integrity and ownership of its data is not a scientific instrument.

The orbital layer, when used, receives compressed knowledge graphs, not raw data. The raw empirical record stays with the operator.

---

### VI. What the Platform Is Not

| Not | Why |
|---|---|
| A self-driving vehicle | The platform does not drive itself |
| A surveillance system | No facial recognition, no tracking |
| A synthesis laboratory | It observes, it does not produce |
| A replacement for human judgment | The operator is the final arbiter |
| A finished product | It is an engineering specification |

The platform is a research instrument. It is designed to be built, tested, and improved.

---

### VII. The Long View

The most valuable asset in AI is not code. It is verified experience of physical reality. Text corpora are finite, contaminated, and increasingly synthetic. Physical measurement is neither.

A network of instruments that collect first-principles data, validate it locally, and share compressed knowledge graphs is a different kind of AI infrastructure. It does not depend on the internet. It does not depend on a single vendor. It depends on the physical world, which is the one resource that cannot be scraped.

DAXSI is one instrument in that network. It is not the network itself.

## AI Layer

Three layers, each with a distinct role.

| Layer | Role | Implementation | Status |
|---|---|---|---|
| Local backbone | Zero-latency inference, offline autonomy | Open-weights 70B, 4-bit AWQ, model-agnostic | `[COTS]` |
| Orbital validation | Cross-check, enrichment, weight updates | xAI Grok via Starlink | `[COTS]` |
| Human-in-the-Loop | Final arbitration, annotation, LoRA/QLoRA triggers | Operator console | `[COTS]` |

The local backbone is model-agnostic by design. Any open-weights checkpoint can be substituted. The orbital layer is xAI-specific by project intent, consistent with the Cybertruck / Starlink platform.

## Power Budget

Baseline draw from Cybertruck Powershare 240V NEMA 14-50 outlet, 9.6 kW continuous.

| Load | Peak | Average | Notes |
|---|---|---|---|
| Node 02 (4 RTX 6000 Ada) | 1.2 kW | 0.8 kW | Inference bursts |
| Node 01 (2 AGX Orin) | 0.12 kW | 0.08 kW | Continuous |
| Node 03 (8 Orin NX) | 0.16 kW | 0.12 kW | Continuous |
| Cooling loops | 0.3 kW | 0.15 kW | Variable |
| ECLSS + climate | 0.4 kW | 0.2 kW | Variable |
| Sensors | 0.15 kW | 0.1 kW | Continuous |
| **Total** | **2.33 kW** | **1.45 kW** | Within 9.6 kW envelope |

Peak headroom is sufficient for transient bursts. Static monitoring states draw approximately 1.5 kW, consistent with multi-week station-keeping on traction battery reserves.
